# Устройство кода и руководство по изменению

## 1. Назначение и границы модулей

Сервер состоит из независимо проверяемых слоёв. Направление зависимостей: HTTP знает сценарии usecase, usecase знает доменные модели и собственные интерфейсы, конкретные хранилища и медиадвижок подключаются в `cmd/guard/main.go`. Веб-интерфейс обращается только к API своего Go-сервера.

```text
cmd/guard/main.go                    composition root, запуск и остановка
internal/app/domain/models.go       данные и бизнес-валидация
internal/app/repository/settings.go  атомарное файловое хранение политики
internal/app/repository/journal.go   JSONL-журнал, ротация, поиск
internal/app/usecase/service.go      сценарии приложения и состояние
internal/app/media/engine.go         gortsplib RTSP + Pion WebRTC
internal/app/media/h265.go           RFC7798, HEVC profile, проверка SDP
internal/app/media/frames.go         сборка целых RTP-кадров, лимиты очереди
cmd/streamcheck/main.go              измерение RTSP без браузера
internal/app/delivery/http/          маршруты, авторизация, JSON, SSE, SDP
web/embed.go                        встраивание ресурсов в exe
web/index.html                      структура всех страниц
web/assets/styles.css               оформление и адаптивность
web/assets/app.js                   интерфейс и HTTP/SSE-клиент
web/assets/player.js                собственный WebRTC-плеер
```

Это один локальный сервис, а не набор микросервисов. Подход к разделению domain/repository/usecase/delivery взят как архитектурный ориентир из указанного Smart-Catch-Up; код сценариев написан заново под охранную систему.

## 2. Точка входа — cmd/guard/main.go

`main` вызывает `run`; при ошибке печатает её и завершает процесс с ненулевым кодом. `run`:

1. Читает `-listen`, `-data` и переменные авторизации.
2. Проверяет пароль при прослушивании вне loopback и длину токена агента.
3. Создаёт каталог данных, structured logger `slog`, репозитории.
4. Создаёт корневой контекст отмены через `signal.NotifyContext`.
5. Создаёт встроенный `media.Engine` и передаёт его сценарию `usecase.Service`.
6. Собирает HTTP-маршруты и HTTP-сервер с ограничениями заголовков/чтения.
7. Запускает монитор политики и HTTP-сервер.
8. При `Ctrl+C` отменяет корневой контекст, завершает SSE и RTSP/WebRTC, даёт HTTP-серверу время на завершение.

Статика находится внутри exe благодаря `go:embed`. Запуск из другой папки влияет только на относительный `-data`, поэтому сценарий `start.cmd` предварительно переходит в корень приложения.

## 3. Домен — domain/models.go

### Settings

Хранит желаемую конфигурацию: `revision`, `camera_name`, `source`, `preview_enabled`, `armed`, `confidence`, таймеры и `roi`. Содержит данные, но не HTTP-запросы и не операции диска.

`DefaultSettings` задаёт начальную камеру `192.168.1.199`, confidence 0.5, пребывание 30 с, cooldown 60 с. `Validate` проверяет схему RTSP/RTSPS, наличие узла, размеры строк, допустимые числовые диапазоны, конечность float и прямоугольник в пределах кадра. `ValidationError` содержит машинное имя поля и понятный текст.

`PublicSource` удаляет userinfo, query и fragment адреса. Используется в статусе; полный адрес остаётся доступным администратору в настройках и агенту с отдельным токеном.

### ROI

`x/y` — левый верхний угол, `width/height` — размеры, все значения нормированы к полному кадру. `enabled` определяет, должна ли зона использоваться агентом. Это не координаты CSS и не координаты входа нейросети 640×640: преобразование выполняет сам агент для своего кадра.

### Event

Событие включает серверные ID/UTC-время, уровень, тип, источник, сообщение, необязательные track ID/confidence. `Validate` ограничивает размер и значения входных данных. Сервер назначает ID/время самостоятельно, источник входного события фиксирует как `detector`.

### Telemetry

Реальные показатели агента: модель, FPS инференса, время обработки, люди/автомобили, применённый `armed`, применённая `policy_revision`. Сервер ставит своё `received_at`; клиент не может подменить время свежести. `Validate` отклоняет некорректные/бесконечные показатели.

### StreamStatus и Status

`StreamStatus` — снимок медиадвижка: включено ли чтение (`registered`), установлен ли RTSP (`online`), есть ли свежие RTP-пакеты (`has_producer`), байты, кодек, состояние, ошибка, число зрителей и последний пакет. Исторические имена `registered/has_producer` сохранены как поля API и означают состояние встроенного движка, не внешнего приложения.

`Status` объединяет серверное время, состояние камеры, желаемую политику, свежесть/подтверждение агента, журнал и вложенный `stream`. Показатели браузерного декодера сюда не входят: их измеряет плеер.

## 4. Репозитории

### SettingsFile

`Load` читает `settings.json`. Отсутствующий файл означает первый запуск и приводит к значениям по умолчанию. Повреждённый JSON или недопустимая сохранённая политика останавливают запуск с ошибкой: настройки не сбрасываются молча.

`Save` сначала валидирует объект, пишет временный файл **в том же каталоге**, вызывает `Sync`, закрывает файл и заменяет основной через `Rename`. До успешного сохранения сценарий не меняет состояние в памяти. После ошибки временный файл удаляется. Права запрашиваются 0600; на Windows фактический доступ определяется также ACL каталога.

### Journal

`NewJournal` восстанавливает события из `.2`, `.1`, затем текущего JSONL. Последние 5000 держатся в памяти, ID продолжается с максимального найденного. Невалидные строки пропускаются; неполная последняя строка после сбоя питания не уничтожает остальные события.

`Append` под мьютексом назначает ID и UTC-время, при необходимости ротирует файлы 5 МиБ, дописывает JSON-строку и синхронизирует запись. Если предыдущий файл закончился оборванной строкой без перевода строки, перед новой записью добавляется разделитель: следующее корректное событие не склеится с фрагментом. В память событие попадает только после успешной записи.

`List` фильтрует копию индекса и возвращает записи от новых к старым. `Size` возвращает размер индекса. Индекс и записи защищены `RWMutex`. Это файловое хранилище для одного процесса; для нескольких серверов замените репозиторий на транзакционную БД.

## 5. Сценарии — usecase/Service

Зависимости описаны интерфейсами `SettingsRepository`, `EventRepository`, `StreamGateway`. Их можно заменить без переписывания HTTP. Конструктор `New` загружает/сохраняет начальную политику и записывает запуск.

| Метод | Назначение |
|---|---|
| `Settings` | Копия текущей политики |
| `Update` | Валидация, проверка revision, сохранение, аудит |
| `saveLocked` | Общий последовательный путь изменения конфигурации |
| `Preview` | Изменить желаемый просмотр/источник, синхронизировать движок |
| `Arm` | Сохранить желаемый режим, не выдавая его за исполненный |
| `Monitor` | Каждые 3 с синхронизировать политику и статус |
| `Refresh` | Start/Stop движка, обновление снимка и битрейта, события RTSP |
| `Status` | Собрать статус, вычислить свежесть и подтверждение агента |
| `Telemetry` | Проверить показатели, поставить received_at, записать подключение агента |
| `Ingest` | Принять реальное событие детектора в журнал |
| `PlayerEvent` | Принять только известный тип события плеера, ограничить повторения |
| `Events` | Получить отфильтрованный журнал |
| `audit` | Записать собственное событие; ошибку диска вывести через slog |

`opMu` сериализует сохранения и управление источником, `mu` защищает короткие снимки памяти. Сетевой/дисковый ввод-вывод не выполняется под `mu`. `playerMu` ограничивает повторяющиеся события плеера между вкладками.

Каждая запись повышает revision. HTTP 409 защищает от потери изменений другой вкладки. Файл политики и журнал не являются одной транзакцией: политика может сохраниться, а аудит не записаться при последующем сбое диска; ошибка аудита попадёт в stderr сервера.

Подтверждение охраны: `agent_online = age(received_at) < 15s`; `policy_applied = agent_online && reported_revision == desired_revision && reported_armed == desired_armed`. Поэтому неподключённый агент не может означать «охрана работает».

## 6. Видеодвижок — media/Engine

### Управление источником

`New` создаёт движок с корневым контекстом. `Start` идемпотентен для того же включённого источника. Для нового источника он отменяет старый worker, повышает generation, закрывает старые WebRTC-сеансы и запускает чтение в фоне. `Stop` отменяет чтение и зрителей. `Close` дополнительно ждёт завершения фонового RTSP-worker. `Status` возвращает копию данных без блокирующей сети.

`generation` не позволяет запоздалому callback старой камеры перезаписать состояние новой. Все операции Start/Stop сериализованы `control`; состояние и map зрителей защищены `mu`.

### RTSP

`run` восстанавливает поток с паузами 1, 2, 4, 8, 15 секунд. `read` создаёт gortsplib Client, выбирает TCP interleaving, выполняет `DESCRIBE → SETUP → PLAY`, находит **H.265 либо H.264** и регистрирует callback RTP. Для H.265 требуется `sprop-max-don-diff=0`; для H.264 поддерживаются packetization-mode 0/1. Read timeout — 8 с, write/dial timeout — 5 с. Контекст отмены закрывает клиент, прерывая ожидающий сетевой ввод-вывод. Для RTSPS проверяется сертификат стандартным TLS-клиентом.

`publicError` классифицирует ошибки (тайм-аут, отказ, 401, 404, неподдерживаемый кодек) и не возвращает сырую строку библиотеки: она могла бы содержать пароль RTSP.

### RTP и подключение позднего зрителя

`broadcast` увеличивает реальные счётчики байтов/последнего пакета, сохраняет SPS/PPS из SDP и одиночных/STAP-A NAL, распознаёт начало IDR. `frameAssembler.push` в `frames.go` группирует RTP по timestamp до Marker; только завершённый кадр поступает зрителям. Неполный кадр при разрыве sequence number или смене timestamp отбрасывается, зрители ждут новый ключевой кадр. Повтор последнего пакета игнорируется; переход sequence number через 65535 корректен. Клоны пакетов защищают очередь от повторного использования сетевого буфера.

`nalsInPayload` разбирает одиночные NAL и STAP-A, проверяя длины. `startsIDR` распознаёт одиночный IDR, IDR в STAP-A и начальный FU-A фрагмент IDR. До IDR новый зритель не получает зависимые кадры. `writePackets` перед IDR отправляет SPS/PPS, сохраняет RTP timestamp и пересчитывает sequence number с учётом вставленных пакетов.

`webRTCPayloads` удерживает RTP payload в пределах 1200 байт: большие одиночные NAL превращает в FU-A, большие FU-A дробит с сохранением start/end flags, STAP-A при необходимости разбирает. Marker остаётся только на последнем выходном фрагменте. Это уменьшает зависимость от IP-фрагментации на WebRTC-пути.

Для H.265 файл `h265.go` реализует отдельный RFC7798-путь: `h265NALs` разбирает одиночные NAL и AP (type 48), `h265RandomAccess` распознаёт BLA/IDR/CRA (16–21), включая стартовый FU (49). `h265WebRTCPayloads` сохраняет двухбайтовый NAL-заголовок, layer/temporal ID и start/end flags при дроблении до 1200 байт. `broadcast` кеширует VPS/SPS/PPS (32/33/34), `writePackets` вставляет их перед ключевым кадром. Это изменение упаковки сжатых байтов, без декодирования и изменения качества.

Очередь — 4 целых кадра на зрителя. Один большой ключевой кадр больше не переполняет очередь из-за количества его RTP-фрагментов. Кадр ограничен 8 МиБ / 8192 пакетами. При переполнении очередь очищается, зритель ждёт новый IDR, сервер запрашивает ключевой кадр. Writer также отбрасывает кадр, пролежавший в очереди больше 250 мс; это предел ожидания перед отправкой, а не гарантия полной задержки. Медленный браузер не останавливает чтение камеры. Максимум — 8 зрителей. При RTSP-обрыве зрители текущей generation закрываются.

### WebRTC и ресурсы

`Answer` принимает SDP offer, проверяет готовность источника и лимит зрителей, создаёт Pion PeerConnection и TrackLocalStaticRTP с реальным H.264/H.265 источника, согласует профиль по SPS, собирает локальные ICE-адреса и возвращает SDP answer + случайный ID зрителя. `codecCapability` извлекает HEVC profile/tier/level из SPS; для H.264 использует profile-level-id. `hasVideoCodec` проверяет активный video track и направление offer/answer. `matchingHEVCProfile` исключает несовместимые profile-id, tier-flag и tx-mode: MIME-совпадение не преобразует Main10 в Main. Несовместимость оборачивается `ErrBrowserCodec`, HTTP возвращает 422. STUN/TURN не настраиваются; loopback-candidates включены для локального просмотра.

RTCP читается постоянно для работы interceptor/NACK. PLI/FIR и подключение зрителя запрашивают ключевой кадр у RTSP-источника; частота ограничена разом в секунду. Если камера игнорирует PLI, нужно дождаться её следующего IDR/GOP.

`CloseViewer` удаляет зрителя, отменяет writer и закрывает PeerConnection. Удаление повторяемо. Failed/closed peer удаляется автоматически. Незавершённое согласование закрывается через 20 с. При выходе из страницы браузер дополнительно посылает DELETE. `closeGeneration` закрывает список зрителей вне блокировки, чтобы callback закрытия не создавал deadlock.

**Ограничения:** H.264/H.265, без аудио, без декодирования/перекодирования на сервере. Камера должна давать корректный поток с периодическими ключевыми кадрами, а браузер — поддерживать его декодирование. HEVC зависит от браузера, ОС и доступного декодера. Для доступа через NAT/TURN, постоянного хранения тревог и нагрузки больше одной камеры нужна отдельная конфигурация/нагрузочная проверка.

## 7. HTTP delivery

`handler.go` регистрирует методы и маршруты, преобразует JSON в доменные DTO и ответы. `readJSON` ограничивает тело 16 КиБ, запрещает неизвестные поля и несколько JSON-документов. `fail` отдаёт 400 для валидации, 409 для stale revision, 500 с общим текстом для неожиданной ошибки. Сырые ошибки диска уходят в slog.

`middleware.go` проверяет Basic и отдельный Bearer агента константным сравнением. По умолчанию локальная панель принимает только loopback/localhost Host. Origin/Sec-Fetch-Site защищают от запросов чужого сайта, особенно изменений политики. CSP исключает внешние скрипты, object/frame и внешние fetch-подключения. DOM текста событий создаётся через textContent, а не HTML.

`media.go` обменивается SDP через `POST /api/stream/offer` и закрывает зрителей через DELETE. RTSP-адрес от браузерного предложения не принимается: источник берётся из серверной политики. Нет API исполнения произвольных команд.

`eventStream` — SSE для статуса и журналов, а не видеоканал. Каждые 2 с отправляет status и новые события по ID, поддерживает Last-Event-ID и параметр after. Ограниченное окно хранения означает, что после очень длительного отсутствия клиента нужно заново загрузить журнал REST-запросом. Сервер задаёт дедлайн каждой записи, чтобы медленный клиент не удерживал writer бесконечно.

## 8. Браузер

`index.html` содержит семантические страницы трансляции, журнала, настроек и справки; SVG-иконки находятся в одном sprite. `styles.css` задаёт цвета через CSS variables, сетки desktop и адаптацию до телефона. Внешних сетевых ресурсов нет.

`app.js`:

- `api/action/toast` — запросы с тайм-аутом, блокировка кнопки на действие, сообщения ошибок;
- `setConfig/fillSettings/saveSettings` — форма и сохранение версий;
- `applyStatus/setPlaybackState` — реальные серверные/браузерные состояния;
- `mountPlayer/unmountPlayer/preview/reconnect` — жизненный цикл просмотра;
- `snapshot/download` — локальный PNG и экспорт;
- `videoRect/drawROI/roiPoint/drawPointer/saveROI` — рисование в фактической области кадра с учётом letterbox;
- `loadJournal/renderJournal/renderRecent/acceptEvent` — события и безопасный DOM;
- `connectEvents/serverConnection` — SSE и индикатор потери HTTP-сервера;
- `navigate/bindControls/updateClocks/initialize` — навигация, события и запуск.

`player.js` определяет CustomElement GuardPlayer. `app.js` передаёт ему кодек источника через свойство `codec`. `start` создаёт recvonly transceiver, проверяет `RTCRtpReceiver.getCapabilities('video')`, оставляет подходящие H.264/H.265-кодеки браузера, собирает ICE, посылает SDP своему серверу, принимает answer и подключает MediaStream к video. Отсутствующий кодек, HTTP 422 и ошибка декодера переводят плеер в `unsupported` без автоматических повторов; ручное переподключение доступно. `frameArrived` подтверждает реальные кадры. `measure` измеряет FPS/декодер и джиттер-буфер из getStats. `retry` выполняет backoff до 30 с для временных ошибок. `disconnect/dispose` закрывают peer, таймеры, callback кадров и серверного зрителя. Audio/getUserMedia не используются.

## 9. Как изменять

### Добавить настройку

Добавьте поле в Settings и JSON-tag, значение в DefaultSettings и правило Validate; добавьте элемент формы, чтение в saveSettings и заполнение fillSettings. Существующим settings.json понадобится обратно совместимое значение либо явная миграция. Агент должен понимать поле и подтверждать новую revision.

### Заменить хранилище

Реализуйте SettingsRepository/EventRepository поверх SQLite/PostgreSQL. Сохраните порядок подтверждения записи и правила ID/revision. Подключите новые конструкторы только в main; HTTP и UI менять не требуется.

### Подключить детектор

Используйте `/api/agent/policy`, `/api/agent/events`, `/api/agent/telemetry`. Нельзя подтверждать режим до фактического применения в детекторе. Не подставляйте browser FPS вместо FPS модели. Контракт и пример цикла — в API.md.

### Несколько камер / аудио / перекодирование

Для нескольких камер замените единичный Engine и Settings.Source на реестр источников, каждому назначьте независимый журнал/права/лимиты. Для аудио понадобится отдельный согласуемый WebRTC-кодек и RTP-трек. Для просмотра HEVC в браузере без HEVC-декодера нужен отдельный путь декодирования/перекодирования: существующая передача RTP этого не делает. Эти возможности не включены скрытыми заглушками.

### Подготовка к эксплуатации

Текущая версия — рабочая локальная первая версия с проверяемыми границами. Перед постоянной охраной выполните длительный прогон на реальной камере, тесты обрывов питания/Wi-Fi, проверьте агент, доставку тревог, сохранность файлов и резервное копирование. Список уже выполненных и ручных проверок находится в TESTING.md.
