# Штатный плеер go2rtc внутри панели

Это описание действующего режима. Прежний собственный RTSP/WebRTC-движок и медиапрокси сохранены в репозитории, но не подключены в `cmd/guard`.

## Точки входа

- `cmd/guard/main.go`: создаёт репозитории, сервис, read-only `relay.Gateway` и HTTP-сервер. Не вызывает `EnsureProcess`, `MediaRoutes` или `RelayRoutes`; не запускает go2rtc и не подключается к RTSP камеры.
- `web/assets/player.js`: `STREAM_URL` — штатная страница `/stream.html?src=luckfox` на том же имени/IP, что панель, и порту 1984. При открытии панели на `127.0.0.1` получается прежний адрес `http://127.0.0.1:1984/stream.html?src=luckfox`. `GuardPlayer.start()` добавляет один iframe с разрешениями autoplay/fullscreen/PiP; `dispose()` удаляет его. Нет собственных таймеров восстановления, изменения буфера, форсирования MSE или чтения видеопакетов.
- `web/assets/app.js`: открывает плеер на странице трансляции, закрывает при остановке/переходе в другой раздел, перезагружает по кнопке оператора. Ошибка опроса API go2rtc не пересоздаёт iframe. Состояние `embedded` скрывает заглушку, но не выдаёт загрузку страницы за LIVE.
- `web/assets/styles.css`: iframe занимает окно видео. Прежние внешние часы, LIVE и ROI не накладываются поверх штатного плеера и не закрывают его кнопки.
- `internal/app/relay/gateway.go`: реализует интерфейс `StreamGateway` из usecase. `Start`/`Stop` меняют только локальное состояние наблюдения. Единственный HTTP-метод к go2rtc — GET `/api/streams?src=luckfox`. `Close` ничего не останавливает.
- `internal/app/usecase/service.go`: каждые 3 секунды читает состояние и вычисляет видеобитрейт по разнице накопительных байтов. При смене producer ID счётчик учитывается заново без отрицательного битрейта. Это не измерение FPS или полной задержки.
- `internal/app/delivery/http/handler.go`: в текущем запуске медиамаршруты выключены (`Routes(nil, ...)`). `/api/stream/ws` и `/api/stream/offer` возвращают 404. Интерфейс, политика, журнал, SSE и API агента продолжают работать.
- `middleware.go`: CSP разрешает iframe от того же имени/IP и схемы, что панель, на порту 1984; защита API и проверка origin сохранены.
- `scripts/start-admin.cmd`: запускает только Go-админку. `scripts/start.cmd` отдельно запускает go2rtc и не нужен, если ваш привычный go2rtc уже работает.

## Управление источником

Имя потока фиксировано: `luckfox`. Настраивайте его в YAML отдельно запущенного go2rtc. Если хотите другое имя, согласованно измените `relay.StreamName` и `STREAM_URL`, затем пересоберите панель. Адрес в настройках панели предназначен для агента и не управляет go2rtc.

## Ограничения origin

Порты 8080 и 1984 — разные origin. Панель не получает DOM-видео и статистику декодера из iframe. Поэтому снимок кадра, рисование ROI, FPS, буфер, потери декодера и задержка недоступны. Кнопки плеера go2rtc работают внутри iframe. Кодек и битрейт панели относятся к источнику в go2rtc, а не к факту декодирования кадра в браузере.

Для удалённого браузера плеер использует имя/IP из адресной строки панели; контейнерное имя `go2rtc` в браузер не попадает. Серверный адрес API задаётся отдельно флагом `-go2rtc-url`, в Compose это `http://go2rtc:1984`. Для WebRTC через Docker опубликован порт 8555 TCP/UDP и объявлен адрес хоста `GO2RTC_HOST`. См. [DOCKER.md](DOCKER.md).

## Проверка

1. Запустить существующий go2rtc, затем `scripts/start-admin.cmd`.
2. Открыть панель на 8080, обновить Ctrl+F5. Внутри должен быть тот же штатный плеер, что по прямой ссылке 1984.
3. Сравнивать по очереди: закрыть отдельную вкладку перед просмотром в панели. У встроенного URL нет `mode=mse` или других принудительных режимов.
4. Остановить просмотр: iframe удаляется. Существующий поток и внешний плеер go2rtc не удаляются.
5. Остановить Go-сервер: ваш процесс go2rtc продолжает работать.

Автоматические тесты проверяют отсутствие мутаций go2rtc при Start/Stop/Close и обработку счётчиков после смены producer, а HTTP-тесты — отключённые медиамаршруты и существующую авторизацию. `go test ./...`, `go vet ./...` и `npm run check` не подтверждают плавность живого видео. Её проверяют в браузере на реальном источнике.

## Разбор наблюдавшихся ошибок

`RTP header size insufficient` означает, что go2rtc не смог разобрать полученный буфер как корректный RTP-пакет. В RTSP/TCP это может быть дефектом формирования/разделения пакетов источником или совместимости парсера; сообщение само по себе не доказывает потери Wi-Fi. TCP обычно восстанавливает потерянные сегменты, что проявляется задержками.

`read tcp ...:554: i/o timeout` — чтение от камеры не завершилось за установленное время. Наличие слушающего порта и успешный ping не подтверждают непрерывную выдачу видео.

В проекте go2rtc есть [отчёт о похожем сбое RTSP/TCP](https://github.com/AlexxIT/go2rtc/issues/2574) у другой камеры. Это основание проверять формирование потока, а не установленный диагноз для Luckfox. Увеличение тайм-аута не восстанавливает отсутствующие кадры. Смазывание движения требует отдельной оценки выдержки, освещения и сжатия; по приведённым строкам лога его причину установить нельзя.
