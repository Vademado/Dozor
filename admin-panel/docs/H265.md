# H.265 (HEVC) в панели

Плата уже настроена на H.265, если в `/userdata/rkipc.ini` секции `[video.0]` и `[video.1]` содержат `output_data_type = H.265`. В этом случае менять конфигурацию и перезапускать rkipc для смены кодека не требуется. Приложение получает реальный формат из RTSP SDP, а не из имени URL.

## Как запустить

1. Включите плату и роутер. На компьютере остановите прежнее окно панели сочетанием Ctrl+C.
2. Запустите `admin-panel/scripts/start.cmd`. Если меняли исходники, сначала запустите `build.cmd`.
3. Откройте <http://127.0.0.1:8080> в актуальном Google Chrome и нажмите Ctrl+F5.
4. Укажите `rtsp://192.168.1.199:554/live/0`, нажмите «Запустить».
5. В карточке соединения должен появиться H.265. Успешный просмотр подтверждают LIVE, меняющаяся картинка, ненулевое разрешение и поступление новых кадров. Один статус «RTSP подключён» не подтверждает декодирование.

## Совместимость браузера

Строка «WebRTC браузера» в карточке «Соединение» показывает предлагаемые браузером H.264/H.265 независимо от доступности камеры. Если H.265 там отсутствует, приём HEVC через WebRTC этим браузером недоступен.

Chrome поддерживает HEVC в WebRTC начиная с версии 136, но доступность на конкретном компьютере зависит от платформенного декодера. Поддержка HEVC-файла в обычном `<video>` сама по себе не подтверждает HEVC в WebRTC. Edge и встроенные браузеры могут предлагать другой набор кодеков даже на том же ПК.

Панель проверяет `RTCRtpReceiver.getCapabilities('video').codecs`, затем реальный SDP offer/answer и, наконец, получение декодированных кадров. Если кодек отсутствует, выводится «Кодек недоступен», а автоматические повторы прекращаются. RTSP-соединение при этом может быть исправным. Для диагностики попробуйте актуальный Chrome, включённое аппаратное ускорение и свежий драйвер видеокарты; это не гарантирует поддержку неподходящего оборудования. Go-сервер не устанавливает системные кодеки.

При необходимости список возможностей можно проверить в консоли разработчика браузера (F12 → Console):

```javascript
RTCRtpReceiver.getCapabilities('video').codecs
  .filter(codec => /h265/i.test(codec.mimeType))
```

Пустой массив `[]` означает, что этот браузер не предлагает H.265 для WebRTC. Непустой список подтверждает возможность согласования, но ещё не успешное декодирование конкретного профиля/разрешения.

Источники: [Chrome: HEVC в WebRTC](https://developer.chrome.com/blog/chrome-136-beta#h265_hevc_codec_support_in_webrtc), [MDN: WebRTC codecs](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/WebRTC_codecs).

## Что происходит в Go

`Luckfox/rkipc → RTSP/RTP по TCP через Wi-Fi → gortsplib → перепаковка RTP H.265 → Pion WebRTC/SRTP → декодер браузера`.

H.265 не превращается в H.264. Сервер сохраняет сжатые NAL, кеширует VPS/SPS/PPS и отправляет их перед ключевыми кадрами поздним зрителям. Большие RTP-пакеты дробятся до payload 1200 байт по RFC7798. Это один Go-процесс, без FFmpeg, go2rtc и запуска внешних программ. Wi-Fi и Ethernet для выбора кодека эквивалентны: меняется сетевой интерфейс, а не формат видео.

Поддерживаются single NAL, AP и FU при `sprop-max-don-diff=0`. H.265 с DONL явно отклоняется. Профиль Main10 не объявляется как Main; профиль и tier должны совпасть с возможностями браузера. Аудио и серверное перекодирование отсутствуют.

Код находится в `internal/app/media/engine.go`, `internal/app/media/h265.go`, `internal/app/delivery/http/media.go` и `web/assets/player.js`. Подробности функций — в [CODE.md](CODE.md), HTTP 422 — в [API.md](API.md), проверки и границы подтверждённого — в [TESTING.md](TESTING.md).
