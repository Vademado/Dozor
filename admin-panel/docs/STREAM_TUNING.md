# FPS, плавность и задержка

Четыре разных показателя нельзя подменять друг другом:

- Входящий Кбит/с — фактически полученный видеотрафик, не пропускная способность Wi-Fi. Статичная сцена может иметь маленький битрейт.
- FPS на входе в сервер — завершённые RTP-видеокадры в секунду. Низкое значение означает проблему до браузера: камера, сеть или доставка RTSP.
- FPS просмотра — кадры, представленные браузером. Если входные FPS устойчивы, а здесь провал, проверяйте WebRTC и декодер.
- «Пропущено браузером» — счётчик проигрывателя. «RTP: пропуски / принято» и «WebRTC: потери / принято» — отдельные пакетные счётчики. Они не являются потерями Wi-Fi в процентах.

«Без нового кадра» показывает возраст последней картинки, джиттер-буфер — только один компонент задержки. Ни один из них не измеряет полную задержку от матрицы до экрана. Для такой проверки поместите в кадр часы/секундомер и сравните их с текущим временем.

## Изменения сервера

Вместо очереди на 256 пакетов используется очередь из четырёх целых кадров. Большой IDR не обрывается на середине при переполнении. Незавершённые кадры отбрасываются, после разрыва нужен новый ключевой кадр. Кадры, ожидавшие в очереди более 250 мс, не отправляются. Этот механизм ограничивает накопление на участке Go → браузер, но не удаляет задержку, уже накопленную в камере или TCP.

Браузер запрашивает `jitterBufferTarget=100` мс там, где API доступен. Это пожелание браузеру, не жёсткая гарантия: [описание API](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/jitterBufferTarget). Состояние LIVE снимается, если более двух секунд нет новых кадров; после десяти секунд начинается переподключение. Ошибка декодирования вызывает переподключение, отсутствие поддержки формата — отдельное состояние несовместимости.

Карточка соединения показывает время декодирования кадра по разнице `totalDecodeTime / framesDecoded` за интервал. Для 25 FPS бюджет — около 40 мс на кадр; это ориентир для нагрузки декодера, не полная длительность конвейера.

## Профиль камеры для первой проверки

`scripts/luckfox-smooth.sh` предназначен **для Linux на плате**, не для запуска в Windows. Он устанавливает для `video.0` H.264 Baseline, 1280×720, 25 FPS, GOP 25, CBR 1024 Кбит/с. Это начальная конфигурация для проверки плавности, не обещание максимума конкретного оборудования. Входной FPS сенсора не увеличивается: значение 30 в настройках выхода не создаст кадры, если сенсор выдаёт 25.

Скопировать из PowerShell:

```powershell
scp "scripts/luckfox-smooth.sh" root@192.168.1.199:/tmp/luckfox-smooth.sh
```

Команда дана для рабочего каталога `admin-panel`. На плате:

```sh
sh -n /tmp/luckfox-smooth.sh
sh /tmp/luckfox-smooth.sh
```

Скрипт проверяет известный блок вашей прошивки в `/oem/usr/bin/RkLunch.sh`. Там заводской INI копировался в `/userdata/rkipc.ini` безусловно при каждом старте, поэтому редактирование одного INI терялось после reboot. Скрипт восстанавливает условие «только если INI отсутствует», делает резервные копии INI и загрузочного скрипта в `/userdata`, останавливает только `rkipc`, дожидается завершения, записывает профиль и снова запускает камеру. Он не вызывает `S21appinit stop`: штатный stop дополнительно завершает DHCP-клиенты.

При доступном для записи `/etc/init.d` создаётся `S99dozorwifiperformance`, который после подключения к точке доступа отключает Wi-Fi power save. Загрузка не блокируется, ожидание ограничено 30 секундами. Настройки подключения и пароли Wi-Fi не меняются. Журналы — `/tmp/rkipc-smooth.log` и `/tmp/dozor-wifi-performance.log`.

Пути резервных копий печатаются при применении. Для отката сначала остановите только `rkipc`, дождитесь его завершения, восстановите нужный INI и при необходимости `RkLunch.sh` из напечатанных копий, затем перезапустите плату. Для отмены автоматического power-save off удалите созданный `/etc/init.d/S99dozorwifiperformance` или восстановите его резервную копию. Не удаляйте остальные init-скрипты.

## Независимое измерение

Закройте просмотр и другие RTSP-плееры, чтобы измерять один сеанс. В PowerShell из `admin-panel`:

```powershell
.\dist\streamcheck.exe -source rtsp://192.168.1.199:554/live/0 -duration 30s
```

Сборка инструмента: `go build -o dist/streamcheck.exe ./cmd/streamcheck`. Он использует ту же Go-библиотеку RTSP, без браузера/WebRTC и внешних программ. Каждые три секунды выводит JSON: кодек, средний FPS завершённых видеоданных, Кбит/с, ключевые кадры, отсутствующие RTP-пакеты, ошибки сборки и максимальную паузу между пакетами. SPS/PPS/VPS без изображения в FPS не считаются. Это проверка транспорта сжатого видео; она не подтверждает визуальное качество декодирования.

Измеряйте неподвижную и движущуюся сцену при достаточном освещении. Сравнивайте несколько десятков секунд, а не один скачок FPS. При стабильных входных 25 FPS и низких браузерных проверяйте декодирование и WebRTC. При низких входных FPS смена браузера не исправит поступление кадров. Повышение битрейта не создаёт недостающие кадры, а увеличение буфера добавляет задержку.

Для просмотра с низкой задержкой H.264 часто проще по совместимости. H.265 при том же качестве экономит трафик; выбор зависит от аппаратного декодера и реальной сети. Поддержка форматов в RKIPC: [исходник RV1106 Luckfox](https://github.com/LuckfoxTECH/luckfox-pico/blob/main/project/app/rkipc/rkipc/src/rv1106_ipc/video/video.c).
