# Проверки и эксплуатационные ограничения

## Автоматические проверки

Запуск: `scripts/test.cmd`, либо `go test ./...` и `go vet ./...` при Go 1.26+. Интеграционные тесты создают временные локальные сетевые соединения. В изолированной Windows-среде доступ к localhost может требовать разрешения среды выполнения.

Проверяются:

- восстановление настроек после перезапуска и отказ от записи некорректной политики;
- продолжение ID журнала, фильтры, восстановление после оборванной последней JSONL-строки;
- независимость остановки просмотра от режима охраны;
- отклонение устаревшей revision и подтверждение политики только свежим агентом с теми же revision/armed;
- Basic/Bearer-разделение, Origin/Host, строгий JSON, закрытый API агента без токена;
- встраивание ресурсов и отмена SSE;
- **настоящий сетевой тест RTSP/TCP → встроенный движок → WebRTC/SRTP → второй Pion-клиент**;
- H.264 и H.265 в сетевом тесте; SPS/PPS либо VPS/SPS/PPS перед ключевым кадром для позднего зрителя, непрерывность sequence number после вставок, сохранение RTP timestamp/marker и закрытие сеанса;
- точное восстановление исходных H.265 NAL независимым RFC7798-декодером после дробления single NAL, AP и больших FU, включая переход sequence number через 65535;
- отказ H.264-only браузеру при H.265-источнике без утечки зрителя, проверка HEVC-профиля/направления и HTTP 422 `codec_unsupported`;
- отсутствие RTSP-пароля в диагностических текстах.
- целый ключевой кадр из 500 RTP-фрагментов как одна запись очереди; отбрасывание кадра с отсутствующим фрагментом, повтор пакета, смена timestamp и переполнение sequence number.

RTSP-fixture в тесте генерирует протокольные пакеты для проверки транспорта. Он не является демонстрационной камерой и не подменяет видеоданные рабочего интерфейса. Тест не подтверждает декодирование реальной сцены браузером.

## Результат проверки 2026-11-05

`go test ./...`, `go vet ./...`, сборка CGO_ENABLED=0 и синтаксическая проверка JavaScript прошли. Проверены интерфейс браузера, журнал и диагностическое состояние камеры. [Снимок новой панели](screenshots/console.jpg).

После добавления H.265 повторно прошли Go-тесты, vet, сборка и синтаксическая проверка JS. Финальная попытка открыть обновлённую панель на проверочном порту 8081 во встроенном браузере получила `ERR_CONNECTION_TIMED_OUT`, поэтому новая строка возможностей браузера и ветка HEVC визуально не подтверждены. Временный сервер остановлен; пользовательские настройки и журнал не изменялись.

Временный запуск вне изоляции установил RTSP-подключение к `192.168.1.199:554` и получал RTP: в отдельном проверочном журнале появились `rtsp_connected`. Также наблюдались сообщения gortsplib `RTP packets lost` и одно восстановление RTSP. Причина пропусков этим прогоном не установлена; качество и стабильность реального видео нужно проверить отдельно.

После жалобы на зависание отдельный RTSP-замер подтвердил паузы ещё до браузера. В коротком H.265-прогоне основной поток имел примерно 4,8 access unit/с и паузу до 3,13 с; дополнительный — паузу до 5,74 с. После отключения power save и закрытия остальных клиентов основной поток улучшился примерно до 13,6 access unit/с, с паузой до 0,80 с. В раннем диагностическом счётчике учитывались также отдельные parameter-set access units; впоследствии FPS ограничен VCL-видеоданными.

Пользователь применил H.264 Baseline/1280×720/25 FPS/GOP25. Первый reboot сбросил профиль: прочитанный с платы `RkLunch.sh` безусловно копировал заводской INI. Скрипт настройки исправлен, повторное применение подтвердило фактический H.264 в RTSP. После исправления счётчика 30-секундный прямой замер получил 598 видеокадров (19,93 FPS), 214,46 Кбит/с в среднем, 0 пропущенных номеров RTP, 0 ошибок сборки, максимальную паузу 485 мс. Последние 3 с дали 75 кадров (25 FPS). Это не подтверждение постоянных 25 FPS в браузере: исходная доставка всё ещё неравномерна. Инструкции и границы измерений — [STREAM_TUNING.md](STREAM_TUNING.md).

Реальное видео H.265 с платы в браузере пока не подтверждено. Ранее из среды инструментов TCP-соединения на порты 22 и 554 получали тайм-аут, тогда как пользователь в своём PowerShell получил `TcpTestSucceeded: True`, а его экземпляр приложения дошёл до ошибки неподдерживаемого H.265. Это разные результаты окружений; прежний тайм-аут не доказывает неисправность Wi-Fi платы. После добавления HEVC нужно перезапустить обновлённую сборку в пользовательском Windows-сеансе и проверить реальные декодированные кадры.

JavaScript проверяется `npm run check` (Node необязателен для эксплуатации). Go-сборка выполняется с CGO_ENABLED=0; FFmpeg, DLL декодера и внешний медиасервер не требуются.

## Ручная проверка перед использованием

1. Включить роутер и плату. Проверить её актуальный IP, rkipc и порт 554.
2. Запустить только guard-admin.exe и браузер, закрыв прежний внешний видеомост.
3. Указать H.264 или H.265 RTSP-поток. Для HEVC проверить [совместимость браузера](H265.md). Дождаться LIVE и убедиться, что изображение меняется, FPS/разрешение/битрейт появляются из реального видео. При отсутствии кодека ожидается понятное состояние «Кодек недоступен» без бесконечных переподключений.
4. Сделать снимок, открыть PNG и сравнить с текущей сценой.
5. Остановить/запустить просмотр, открыть вторую вкладку, закрыть её и проверить освобождение зрителя.
6. Отключить источник/роутер, проверить сообщение о сбое и восстановление после возврата сети.
7. Открыть журнал, применить фильтры и экспорт, перезапустить сервер и проверить сохранность.
8. Изменить ROI и настройки, проверить после перезапуска. Одновременно сохранить старую форму второй вкладки — ожидается конфликт 409.
9. Подключить реальный агент, применить политику и отправить телеметрию. Проверить отказ от ложного подтверждения старой версии и потерю подтверждения через 15 с тишины.
10. Проверить desktop/mobile, навигацию с клавиатуры и полноэкранный режим.

## Что требует отдельной проверки

- Реальная камера и стабильность Wi-Fi не могут быть подтверждены одним тестовым RTP-fixture. Тайм-аут порта 554 — блокирующее условие для реального изображения.
- Аудио и серверное перекодирование не входят в эту версию. H.265 без DONL поддерживается; наличие совместимого декодера браузера проверяется на конкретном компьютере.
- Сложный NAT/доступ из интернета не настроены: STUN/TURN не используются.
- Лимит — одна камера и 8 WebRTC-сеансов; длительная нагрузка на конкретном ПК/плате должна измеряться отдельно.
- Одна папка данных обслуживается одним процессом; сетевые файловые системы, несколько серверов и транзакционная БД не реализованы.
- Для тревожного видеозаписывания, YOLO/трекера, уведомлений и фактического управления режимом нужен агент. Его наличие не симулируется.
- Текущий журнал хранит ограниченное окно, а API событий не имеет idempotency key; для гарантированной доставки нужна доработка агента/хранилища.

Система является первой локальной версией панели. Постоянную эксплуатацию охраны следует подтверждать длительным прогоном, проверкой ложных тревог, восстановления питания и сохранности доказательных записей в самом агенте.
