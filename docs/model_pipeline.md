# Модель и контур анализа видеопотока

## 1. Требования из ТЗ

ТЗ требует обнаруживать людей и транспортное средство, сохранять track ID, отслеживать движение в контролируемой зоне, измерять непрерывное время нахождения, обнаруживать подозрительные паттерны, записывать доказательства, вести журнал и уведомлять владельца через VK. В документе также указана проверка исчезновения транспортного средства после калибровки.

## 2. Почему нужна не только YOLO

YOLO выдаёт для кадра прямоугольники, классы и вероятности. Он не обязан сохранять ID между кадрами и не знает, сколько человек уже находится в зоне. Поэтому полный алгоритм делится на слои:

```text
камера -> YOLOv8n/RKNN -> ByteTrack -> ROI и таймеры
                                      -> анализ траекторий
                                      -> контроль vehicle
                                      -> журнал + pre-roll/post-roll + VK
```

Для RV1106 детектор должен работать на NPU, а трекинг и правила — на CPU. Нельзя отправлять в NPU отдельную нейросеть для каждого требования: это ухудшит задержку и расход памяти.

## 3. Разметка датасета

Дообучение не является обязательным для первого запуска. Официальные веса YOLOv8, обученные на COCO, уже умеют находить `person` (класс 0) и `car` (класс 2). Это позволяет сначала проверить камеру, частоту кадров, трекинг и правила событий. Однако такая модель не знает конкретный ракурс, ночную ИК-сцену и особенности автомобиля владельца.

Датасет должен состоять из кадров с предполагаемой камеры и точки установки, а не только из кадров COCO. Минимальный набор классов:

- `person` — любой человек, включая частично закрытого человеком или автомобилем;
- `vehicle` — охраняемый автомобиль в разных ракурсах, при открытых дверях и частичном перекрытии.

Нужно включить дневные и ночные кадры, дождь/снег при наличии, пустую сцену, нескольких людей, людей у автомобиля, быстрые проходы по краю кадра и типичные ложные объекты. Разделение train/val/test выполняется по видеосценам или временным отрезкам, а не случайно по соседним кадрам, иначе метрика будет завышена.

Рекомендуемая начальная цель — 1500-3000 кадров, из них не менее 20% ночных или сложных. Для курсового проекта важнее полнота обнаружения человека в зоне, чем детекция редких классов вне зоны.

Структура:

```text
dataset/
  images/{train,val,test}/
  labels/{train,val,test}/
```

Каждая строка label имеет формат YOLO: `class x_center y_center width height`, координаты нормированы от 0 до 1.

## 4. Обучение

Базовый запуск на GPU:

```bash
pip install ultralytics pyyaml
python scripts/train_yolov8.py \
  --data configs/data.yaml \
  --model yolov8n.pt \
  --imgsz 640 \
  --epochs 100 \
  --device 0
```

После обучения нужно сохранить `best.pt`, значения precision/recall/mAP50-95, матрицу ошибок и примеры ошибок на тестовых сценах. Не следует переходить к плате, если модель уверенно находит человека только на светлых кадрах.

## 5. Экспорт для RV1106

Последовательность из используемого туториала:

1. обучить YOLOv8n на GPU;
2. экспортировать граф без NMS и DFL в ONNX через форк Ultralytics, ориентированный на RKNN;
3. сконвертировать ONNX в RKNN INT8 с калибровочным набором кадров;
4. проверить модель на ПК, затем на точной ревизии прошивки и платы;
5. собрать C++-демо под ARMv7 hard-float, положив рядом `.rknn`, `labels.txt` и RKNN runtime.

Калибровочные кадры должны быть похожи на реальные кадры установки: 100-300 изображений обычно достаточно для первого прогона. После INT8 нужно сравнить результаты с `best.pt` на одном и том же тестовом наборе.

У RV1106 есть ограничения по памяти и совместимости runtime. В официальном RKNN Model Zoo для RV1106/RV1103 поддержка обозначена как ограниченная, поэтому перед фиксацией YOLOv8 необходимо выполнить board smoke test. Если custom YOLOv8 не запускается на конкретной версии firmware/runtime, запасной путь — YOLOv5n с теми же двумя классами и тем же постпроцессингом.

## 6. Правила первого функционального прототипа

Пусть `zone` — полигон охраняемой зоны, `vehicle_roi` — область, где ожидается автомобиль.

Для каждого track ID хранятся `first_seen`, `last_seen`, последняя точка центра, траектория и флаги пересечения зон. Временная потеря детекции не должна немедленно создавать новый ID: используется буфер пропусков `max_age`.

События первого прототипа:

- `DWELL_TIMEOUT`: человек непрерывно находится в `zone` дольше `dwell_seconds`;
- `APPROACH_VEHICLE`: человек вошёл во внутреннюю область вокруг автомобиля;
- `SUSPICIOUS_MOTION`: резкое ускорение, частые смены направления или повторное пересечение границы;
- `VEHICLE_MISSING`: автомобиль отсутствует несколько последовательных кадров после калибровки;
- `VEHICLE_MISSING_WITH_PERSON`: `VEHICLE_MISSING`, связанное с ближайшим активным человеком.

Событие должно иметь `event_id`, UTC timestamp, `track_id`, тип, confidence/основание, путь к видео и снимок кадра. Одинаковое событие не отправляется в VK на каждом кадре: используется cooldown и подтверждение несколькими кадрами.

## 7. Доказательная запись и VK

Видеозапись должна включать кольцевой буфер до события и хвост после события. На плате запись следует выполнять через аппаратный кодер/медиатракт Luckfox, а не рассчитывать на тяжёлый `cv2.VideoWriter` как на производственный вариант. VK-уведомление — отдельный сетевой модуль с токеном только в переменных окружения или защищённом конфиге; токен нельзя хранить в модели, датасете или Git.

## 8. Критерии приёмки первого этапа

1. На тестовом видео detector не теряет человека при кратком перекрытии.
2. Один проход человека даёт один track ID с допустимым числом переидентификаций.
3. Таймер зоны срабатывает только после заданного интервала и не дублирует событие.
4. Исчезновение автомобиля подтверждается несколькими кадрами и не срабатывает от единичного пропуска.
5. Журнал связывает событие с `track_id` и timestamp.
6. На RV1106 измерены FPS, задержка, RAM и температура в длительном прогоне.

## 9. Что нужно измерить на плате

Минимальный протокол: разрешение и FPS камеры, размер входа, среднее и 95-й перцентиль времени инференса, полная частота контура, пиковая RAM, число пропусков кадров, стабильность ID на 10-минутной и 1-часовой сценах. Ориентир туториала по YOLOv8 на близкой плате — около 10-15 FPS при 640x640 и 40-50 FPS при 320x320, но это не гарантия для Pico Ultra RV1106.
